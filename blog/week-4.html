Week 4: The LLM Brain: From Prompt Bloat to Local Containerized Orchestration

Welcome to Week 4 of building VITA! Last week, we achieved an exciting physical milestone on our hardware bench: our Raspberry Pi 4 could capture human speech through our I2S MEMS microphone array and speak back with a natural neural voice via Piper TTS. The device had working ears and a working voice. But it still lacked the most critical component of all: a brain.

We needed a language layer capable of parsing natural, unstructured human food requests ("Hey VITA, I just had two scrambled eggs with olive oil and half an avocado") into actionable, clinically defensive nutritional facts. This week, we plunged into the world of Large Language Models (LLMs) on embedded hardware. What started as simple API calls to OpenAI rapidly evolved into an architectural revolution: overcoming prompt bloat, transitioning the LLM into a structured intent orchestrator, hitting a dependency wall on bare metal, and finally containerizing our first local neural model—Qwen—directly on the Raspberry Pi 4.

How do you connect speech-to-text to text-to-speech without creating a sluggish, hallucinating monster? Below is the architectural progression that transformed our voice pipeline this week:

Figure 1: The architectural evolution of VITA's language engine in Week 4, progressing from direct cloud prompt generation to containerized local intent orchestration.

Phase 1: Direct OpenAI Calls & The Prompt Bloat Nightmare

At the beginning of Week 4, our implementation was straightforward: once our local faster-whisper engine transcribed audio into text, the Raspberry Pi made an HTTPS API call to OpenAI (testing both GPT-3.5 and early GPT-4 endpoints). Whatever answer the LLM returned was piped directly into Piper TTS to be spoken aloud.

At first, it seemed to work. But we wanted VITA to behave like a medical-grade nutrition expert, not a generic chatbot. So we started crafting behavioral rules and safety prompts attached to every single user query:

  • Tone & Persona: "Speak concisely, professionally, and never use markdown symbols, asterisks, or bullet points."
  • Portion Defaults: "If grams are omitted, assume standard culinary weights (1 apple = 182g, 1 egg = 50g)."
  • Clinical Guardrails: "Never diagnose illness, always caution about allergens (peanuts, gluten, dairy), and never prescribe pharmaceutical regimes."
  • Brevity Mandate: "Keep responses under 35 words so speech playback finishes quickly."
scripts/llm_orchestration_benchmarks/01_bloated_cloud_prompt_test.py Python 
# The monolithic prompt bloat that choked our context window
MONOLITHIC_SYSTEM_PROMPT = """
You are VITA, a defensive, scientifically grounded Whole Food Intelligence Assistant.
1. Maintain a warm, concise voice suitable for TTS. Never use markdown, bullets, or emojis.
2. Estimate macronutrients (Calories, Protein, Carbs, Fat) strictly based on USDA/CIQUAL reference data.
3. If user omits weight, assume standardized portions (1 apple = 182g, 1 egg = 50g) and state weight clearly.
4. Issue subtle safety warnings for 14 major allergens (Dairy, Gluten, Nuts, Soy, Shellfish...).
5. Keep responses strictly under 35 words so audio playback finishes fast.
6. Do not repeat pleasantries ("Sure thing!", "I would love to help!"). Start immediately with the answer.
... [40 additional clinical rules] ...
"""

# Appended to every 5-word user audio query
payload = {
    "model": "gpt-4o",
    "messages": [
        {"role": "system", "content": MONOLITHIC_SYSTEM_PROMPT},
        {"role": "user", "content": "I had a sliced apple for an afternoon snack."}
    ]
}

What Happened: The Context Window Collapse

Over just 4 days of testing, this approach completely broke down:

1. Prompt Bloat: A simple 8-word user request ("I just ate a banana") required sending over 1,600 tokens of system rules across the wire on every turn. Our context window was filled with repetitive instructions, costs inflated, and network round-trip latency surged past 4.2 seconds.

2. Conversational "Fluff" Ruined TTS: Despite explicit instructions to remain under 35 words, the LLM constantly output conversational filler: "Hello there! I'd be happy to log that healthy snack for you! One medium apple contains approximately 95 calories and 25 grams of carbs. Great job keeping your energy up today!" Having to stand in your kitchen listening to a speaker drone on for 22 seconds to report a 95-calorie apple was an intolerable user experience.

Phase 2: The Architectural Pivot: The LLM as an Orchestrator

We realized we were misusing the LLM. An autonomous food device does not need a language model to perform free-form creative writing. The LLM should be an Orchestration Layer, not a conversational author.

We tore down the architecture and replaced it with a clean, two-step decoupled workflow:

  1. Intent Classification & Slot Extraction: The LLM's sole responsibility is to inspect the user's spoken transcript, categorize it into a closed set of system intents (e.g., LOG_FOOD, QUERY_NUTRITION, ALLERGEN_CHECK), and extract the specific entity parameters (food item, numeric quantity, unit of measurement) into clean, strict JSON.
  2. Deterministic Message Template Injection: The core system takes the extracted JSON slots, looks up the accurate verified data from local tables, and injects the values into pre-approved, medically defensive response templates.
scripts/llm_orchestration_benchmarks/02_structured_intent_template_router.py Python 
# Lean orchestrator prompt: 82 tokens instead of 1,600!
ORCHESTRATOR_PROMPT = """
Extract intent and food entities into valid JSON matching this schema:
{"intent": "LOG_FOOD"|"QUERY_NUTRITION", "food": str, "quantity": float, "unit": str}
"""

# The LLM emits pure, structured data
extracted_json = {
    "intent": "LOG_FOOD",
    "food": "sliced apple",
    "quantity": 182.0,
    "unit": "grams",
    "calories": 95,
    "protein": 0.5
}

# The system injects into deterministic, tested voice templates:
INTENT_TEMPLATES = {
    "LOG_FOOD": "Logged {quantity} {unit} of {food}. Total: {calories} calories and {protein}g protein.",
    "QUERY_NUTRITION": "{quantity} {unit} of {food} contains {calories} calories."
}

# Result spoken by TTS: "Logged 182.0 grams of sliced apple. Total: 95 calories and 0.5g protein."
# Concise, deterministic, zero fluff!

The Breakthrough of Structured Orchestration

This single shift changed everything. By reducing the LLM's role to extracting structured JSON, our prompt size collapsed from 1,620 tokens to just 82 tokens. Conversational hallucinations vanished. And most importantly: because the model no longer needed billions of parameters to hold complex conversational personas, it became realistic to run the LLM locally on the Raspberry Pi 4!

Phase 3: The Bare-Metal Wall & The Shift to Docker Containers

Energized by our intent orchestration breakthrough, we attempted to install a local LLM runtime (llama.cpp / Python llama-cpp bindings) directly on our bare-metal Raspberry Pi 4 host alongside our existing faster-whisper and piper-tts virtual environments.

The Bare-Metal Dependency Hell

Running three complex neural stacks side-by-side on bare-metal Debian Linux became an unmanageable disaster:

  • Shared Library Collisions: llama.cpp required a bleeding-edge version of libstdc++6 and custom OpenBLAS flags that broke CTranslate2's ARM NEON runtime in faster-whisper.
  • Python Wheel Incompatibilities: Upgrading PyTorch dependencies for one package downgraded tokenizers needed by another.
  • Uncontrolled Memory Spikes: When a heavy LLM token generation ran on bare metal, it starved the ALSA audio daemon, causing buffer underruns and audio playback dropouts.

We realized that building a robust, production-grade embedded appliance required strict service isolation. We made the pivotal architectural decision to abandon bare metal and transition to Docker containers.

Figure 2: The containerized microservice topology established in Week 4, isolating audio devices, model runtimes, and HTTP endpoints.

We wrote a clean docker-compose.yml file orchestrating our isolated services, passing /dev/snd only to the containers that actually needed physical hardware access:

docker-compose.yml YAML 
version: "3.8"

networks:
  vita_net:
    driver: bridge

services:
  stt:
    image: vitadevice-stt:latest
    devices:
      - "/dev/snd:/dev/snd"
    environment:
      - MODEL_SIZE=tiny.en
      - COMPUTE_TYPE=int8
    ports:
      - "8001:8001"
    networks:
      - vita_net

  ollama:
    image: ollama/ollama:latest
    volumes:
      - "./models/ollama:/root/.ollama"
    ports:
      - "11434:11434"
    networks:
      - vita_net

  tts:
    image: vitadevice-tts:latest
    devices:
      - "/dev/snd:/dev/snd"
    environment:
      - VOICE_MODEL=en_US-lessac-medium.onnx
    ports:
      - "8002:8002"
    networks:
      - vita_net

Phase 4: Model Selection — Why We Chose Qwen

With our Docker environment stabilized, the question became: Which small local language model can run on an edge device and reliably emit valid JSON without hallucinating or breaking syntax?

We benchmarked four compact open-weights models running 4-bit quantization (GGUF Q4_K_M) inside our Ollama container:

Model Candidate Parameter Size Valid JSON % Token Speed (Pi 4 CPU) Benchmark Evaluation
TinyLlama 1.1 Billion 42.0% 2.8 tok/s Severe syntax failures; emitted unclosed brackets and hallucinations
SmolLM 360 Million 61.5% 5.4 tok/s Fastest, but frequently dropped entity slot keys or inverted quantities
Qwen2.5 (Winner) 500 Million (0.5B) 98.2% 4.6 tok/s Flawless JSON adherence, accurate entities, compact memory footprint
Qwen2.5 1.5 Billion 99.5% 1.9 tok/s Perfect accuracy, but too sluggish for real-time CPU interaction

Qwen was the undisputed champion. Alibaba's Qwen2.5-0.5B displayed an astonishing ability to adhere to strict schema constraints despite its tiny parameter count. It extracted food items, quantities, and units with near-zero syntax errors.

Phase 5: The CPU Reality Check: "Super Slow, But Architecturally Solid"

And now, the honest reality of the engineering bench: Running Qwen2.5 on the Raspberry Pi 4's quad-core Cortex-A72 CPU alongside STT and TTS was super slow.

At an average throughput of 3.4 to 4.6 tokens per second, emitting a 32-token JSON payload took 7 to 9 seconds. When you combine that with STT transcription (~1.0s) and Piper audio generation (~0.4s), the user had to wait over 10 seconds between finishing their sentence and hearing VITA speak.

The Hardware Bottleneck: General-Purpose CPU vs Matrix Compute

A 10-second latency is not fast enough for a consumer kitchen device. But while the raw speed was slow, our software architecture was a massive success:

  • The pipeline was 100% offline: zero third-party cloud dependencies, preserving complete data sovereignty.
  • The system was completely isolated: Docker containers eliminated all library collisions and stabilized ALSA audio threads.
  • The conversational flow was deterministic: structured JSON intent routing completely eliminated hallucinations and prompt bloat.

Week 4 Wrap-Up & Looking Ahead to Week 5

Week 4 was one of the most critical weeks in VITA's history. We solved the conversational intelligence puzzle not by throwing bigger cloud models at the problem, but by engineering an elegant, modular orchestration architecture:

  • Banished prompt bloat by transitioning the LLM into a structured JSON intent extractor.
  • Established microservice containerization with Docker, stabilizing our multi-model runtime environment.
  • Selected Qwen2.5 as our high-precision edge model for schema extraction.
  • Identified the ultimate bottleneck: the Raspberry Pi 4's general-purpose CPU cores simply cannot compute transformer matrix multiplications fast enough.

The software architecture was locked and proven. Now, we had to fix the speed. Next week in Week 5, we leave the Raspberry Pi 4 behind to explore specialized single-board computers equipped with dedicated hardware NPUs (Neural Processing Units)—testing boards like Radxa and the Orange Pi 5 with the RK3588 processor to accelerate our local AI models into sub-second territory!
